# Provenance Guard — Planning Spec

Written before implementation. This document is the contract the code implements, and the
context I hand to AI tools when generating each part (see `## AI Tool Plan`).

---

## 1. Problem and design priorities

A creative-sharing platform wants to tell readers whether a piece of text was written by a
person or generated by AI, without policing creativity. Three priorities drive every decision
below, in this order:

1. **A false positive is worse than a false negative.** Labeling a human's poem "AI-generated"
   damages a real person's reputation. Missing some AI text costs less. So the system needs
   *more* evidence to say "AI" than to say "human", and when unsure it says "unclear", not "AI".
2. **Uncertainty is a first-class answer.** AI detection is an unsolved problem. "We can't
   tell" is an honest, useful result and gets its own label.
3. **Every decision is contestable and reconstructable.** Creators can appeal, and every
   decision and appeal is in an append-only audit log with the signal scores that produced it.

---

## 2. Architecture narrative

A creator's platform sends `POST /submit` with `text` and `creator_id`. The request first
passes the **rate limiter** (per client IP), then **input validation** (text present, 20–10,000
characters). The raw text goes to two independent detection signals:
**Signal 1, the LLM judge** (Groq), which reads the text holistically and returns an
`ai_likelihood` from 0–1; and **Signal 2, stylometry** (pure Python), which measures four
structural properties of the text and returns a `stylometric_score` from 0–1. The **scorer**
combines the two scores into one `ai_score`, shrinks it toward 0.5 when the signals disagree or
the text is short, and applies the asymmetric gates. The **labeler** maps the final score to an
attribution (`likely_ai`, `uncertain`, `likely_human`), a `confidence`, and one of three fixed
label texts. The result is saved to the **content store** (SQLite, status `classified`), written
to the **audit log** (append-only JSONL), and returned to the caller with a `content_id`.

If a creator disagrees, the platform sends `POST /appeal` with that `content_id` and the
creator's reasoning. The appeal handler looks up the original decision, sets the content's
status to `under_review`, writes an appeal entry to the audit log that includes the original
attribution, scores, and the creator's reasoning, and returns a confirmation. A human reviewer
works from `GET /appeals` (the queue). No automated re-classification happens.

---

## 3. Detection signals

Two signals that measure genuinely different properties: one semantic, one structural.

### Signal 1 — LLM judge (Groq)

| | |
|---|---|
| **Measures** | Holistic semantic and stylistic impression: generic vs. specific content, stock phrasing, balanced hedging, absence of a personal stake or concrete lived detail, uniform polish. |
| **Why it differs between human and AI** | LLM output gravitates toward the statistically typical: safe, balanced, generic claims with smooth transitions. Human writing tends to include idiosyncratic specifics (names, places, sensory detail), opinions with stakes, digressions, and imperfections. A language model is good at recognizing "this reads like a language model". |
| **Output** | JSON: `{"ai_likelihood": 0.0–1.0, "indicators": [≤3 short strings], "reasoning": "one sentence"}`. `ai_likelihood` is clamped to [0, 1]. |
| **Model / settings** | Groq chat completion, `temperature=0`, JSON mode. The course lists `meta-llama/llama-4-scout-17b-16e-instruct`; if that model is retired on Groq, use `openai/gpt-oss-120b` (configurable via `GROQ_MODEL` in `.env`). |
| **Calibration instruction** | The prompt tells the model to use the full range, reserve values above 0.85 or below 0.15 for clear cases, and stay between 0.35 and 0.65 when evidence is mixed or the text is very short. |
| **Failure behavior** | API error or unparseable output → the signal is marked `unavailable` (`llm_score: null`). The pipeline continues on stylometry alone, with extra shrinkage, and **cannot** produce a `likely_ai` label. |
| **Blind spots** | (a) It can be fooled by AI text prompted to "write casually with typos". (b) It is biased against formal, formulaic human writing (academic prose, legal text, non-native English writers who learned a formal register), which shares surface features with AI output. (c) It's non-deterministic across model versions, so scores drift if the model changes. (d) It's an LLM judging LLMs, so it shares their blind spots. |

### Signal 2 — Stylometric heuristics (pure Python, no API)

Four sub-metrics, each mapped to 0–1 where **1 = AI-like**, then combined by weighted average.

| Sub-metric | What it computes | Mapping to 0–1 (1 = AI-like) | Weight |
|---|---|---|---|
| **Burstiness** | Coefficient of variation (std / mean) of sentence lengths in words. Sentences split on `.`, `!`, `?` and line breaks. | `clamp((0.70 − cv) / 0.50)`: cv ≤ 0.20 → 1.0, cv ≥ 0.70 → 0.0. **Only computed with ≥ 3 sentences**; otherwise skipped and the other weights are renormalized. | 0.30 |
| **AI stock-phrase density** | Matches per 100 words against a fixed list of phrases LLMs overuse ("it is important to note", "furthermore", "moreover", "paradigm shift", "transformative", "stakeholders", "delve", "tapestry", "navigate the", "in today's", "plays a crucial role", "foster", "leverage", "robust", "seamless", "landscape", "ensure", ...). | `clamp(per_100 / 8)`: 8+ per 100 words → 1.0. | 0.30 |
| **Informality** | Human-casual markers per 100 words: lowercase sentence starts, standalone lowercase "i", contractions, slang/fillers ("lol", "honestly", "kinda", "like,", "ok", "tbh", "gonna"), ALL-CAPS emphasis words, "!!"/"?!"/"...". | `1 − clamp(per_100 / 6)`: 6+ markers per 100 words → 0.0 (very human). | 0.20 |
| **Average word length** | Mean characters per word. | `clamp((avg − 4.2) / 1.6)`: ≤ 4.2 → 0.0, ≥ 5.8 → 1.0. | 0.20 |

**Why these differ between human and AI:** AI text tends to be uniform in sentence length (low
burstiness), leans on a recognizable set of transitional and corporate phrases, avoids casual
markers, and uses longer, more Latinate words. Human writing, especially informal writing,
varies sentence length a lot and is full of casual markers.

**Why not type-token ratio:** TTR depends heavily on text length (it falls as text gets longer),
so on 50- vs. 500-word submissions it measures length more than authorship. I deliberately left
it out.

**Output:** `{"score": 0.0–1.0, "metrics": {cv, stock_phrases_per_100, informal_per_100,
avg_word_len, sentences, words}, "components": {...each sub-score...}}`.

**Blind spots:** (a) Formal human writing (academic, legal, technical) has long words, few
casual markers, and even sentence lengths, so it scores AI-like. (b) Poetry and song lyrics
break sentence-based metrics: repetition and line breaks distort burstiness. (c) An AI told to
"write casually" adds the exact informal markers this signal rewards. (d) The phrase list is
English-only and goes stale as models change their habits.

### How the signals combine

```
if llm available:
    raw = 0.6 * llm_score + 0.4 * stylometric_score
    disagreement = |llm_score − stylometric_score|
    ai_score = 0.5 + (raw − 0.5) * (1 − 0.5 * disagreement)      # disagreement pulls toward 0.5
else:
    ai_score = 0.5 + (stylometric_score − 0.5) * 0.6              # one signal = less certainty

if words < 60:  ai_score = 0.5 + (ai_score − 0.5) * 0.85         # short texts: less certainty
```

The LLM gets the larger weight (0.6) because it captures meaning and context, which stylometry
can't. Stylometry still gets 0.4 because it's deterministic, explainable, and fails in
*different* situations than the LLM, which is the point of having two signals.

## 4. Uncertainty representation

### What the numbers mean

- **`ai_score`** (0.0–1.0) is the system's single scale. **0.5 means "no idea, a coin flip."**
  0.0 means "confidently human", 1.0 means "confidently AI". A 0.6 means "leans slightly
  toward AI, nowhere near enough to say so".
- **`confidence`** (0.5–1.0) is how sure the system is of the attribution it returns,
  `max(ai_score, 1 − ai_score)`. For example, `likely_human` with `ai_score` 0.12 has
  confidence 0.88.

### Thresholds (asymmetric on purpose)

| `ai_score` | Attribution | Label variant |
|---|---|---|
| **≥ 0.80** *and all AI gates pass* | `likely_ai` | High-confidence AI |
| **0.36 – 0.79** | `uncertain` | Uncertain |
| **≤ 0.35** *and human gate passes* | `likely_human` | High-confidence human |

The uncertain band is wider on the AI side (0.50 → 0.80 is 0.30 wide; 0.50 → 0.35 is 0.15 wide).
Calling something AI requires much stronger evidence than calling it human, because of the
false-positive asymmetry.

### Gates (checked after scoring)

`likely_ai` requires **all** of:
1. the LLM signal is available,
2. `llm_score ≥ 0.65` **and** `stylometric_score ≥ 0.55`, so both independent signals lean AI
   on their own,
3. the text has at least 40 words.

`likely_human` requires the text to have at least 25 words.

If a gate fails, `ai_score` is clamped into the uncertain band (to 0.79 or 0.36) and the
response includes a `gate_note` explaining why (e.g. "signals disagree"). The score and the
label never contradict each other.

### Worked example: a false positive, traced

A graduate student submits a formal paragraph on monetary policy that they wrote themselves.
Stylometry scores it ~0.8 (long words, no casual markers). The LLM scores it ~0.5 ("formal but
specific"). Raw = 0.62, disagreement 0.3 → `ai_score` ≈ 0.60. That's in the uncertain band, so
the label says "Origin unclear", **not** "Likely AI-generated". Even if the LLM had said 0.85,
the student would only be labeled AI if stylometry also cleared 0.55 and the combined score
cleared 0.80. If that happens, the label says the creator can appeal. The appeal sets the
content to `under_review` and puts it in the human review queue with both signal scores, so a
reviewer can see that the stylometry signal (which is known to be biased against formal
writing) drove the score.

## 5. Transparency label design

Three fixed variants. Plain language, no jargon, no percentages a reader could over-trust.
The confidence level is carried by the wording ("strong signs" vs. "couldn't tell"). Every
variant says it's automated.

| Variant | Attribution | Exact label text |
|---|---|---|
| High-confidence AI | `likely_ai` | **"🤖 Likely AI-generated. Our automated checks found strong signs that this text was written with AI. Automated detection can be wrong, and the creator can appeal this label."** |
| High-confidence human | `likely_human` | **"✍️ Likely human-written. Our automated checks found writing patterns typical of a person rather than AI. This is an automated assessment, not a guarantee."** |
| Uncertain | `uncertain` | **"❔ Origin unclear. Our automated checks couldn't confidently tell whether this was written by a person or with AI. Short, formal, or edited writing often gets this result, so please don't treat it as a judgment either way."** |

Design choices:
- **No raw percentage in the reader-facing label.** "87% AI" invites over-trust and makes a
  0.81 look meaningfully different from a 0.84. The API still returns `confidence` for the
  platform, and the platform can show it in a "details" view.
- **The uncertain label explicitly says "don't treat it as a judgment".** A reader seeing
  "unclear" might otherwise assume "probably AI".
- **The AI label mentions the appeal path** because it's the only label that can harm the
  creator.

## 6. API surface

| Endpoint | Accepts | Returns |
|---|---|---|
| `POST /submit` | JSON `{"text": str, "creator_id": str}` | `200 {content_id, creator_id, attribution, confidence, ai_score, label, status, signals: {llm: {score, status, indicators, reasoning}, stylometry: {score, metrics}}, gate_note, timestamp}`. `400` on bad input, `429` when rate-limited. |
| `POST /appeal` | JSON `{"content_id": str, "creator_reasoning": str, "creator_id"?: str}` | `200 {appeal_id, content_id, status: "under_review", original_attribution, original_confidence, message}`. `400` missing fields, `404` unknown id, `403` creator mismatch, `409` already under review. |
| `GET /content/<content_id>` | none | The stored record: attribution, scores, label, status, appeal reasoning if any. |
| `GET /appeals` | none | Review queue: all `under_review` items, oldest first, with original scores, label, and the creator's reasoning. |
| `GET /log?limit=N` | none | `{"entries": [...]}`, the most recent N audit entries (default 50). |

## 7. Appeals workflow

- **Who can appeal:** the creator of the content. The prototype has no login, so the original
  `creator_id` stands in for identity: if the appeal includes `creator_id`, it must match the
  one on the submission (otherwise `403`). In production this check would come from the
  authenticated session.
- **What they provide:** `content_id` and `creator_reasoning` (1–2,000 characters), e.g. "I
  wrote this from personal experience; here's my draft history."
- **What the system does:**
  1. Looks up the content. Unknown id → `404`.
  2. If it's already `under_review` → `409` (no duplicate appeals flooding the queue).
  3. Sets status `classified` → `under_review` in the content store and saves the reasoning
     and appeal timestamp.
  4. Appends an `appeal` entry to the audit log containing the original decision (attribution,
     confidence, ai_score, both signal scores) **and** the appeal reasoning, so the log line
     alone tells the whole story.
  5. Returns a confirmation. No automated re-classification.
- **What a reviewer sees in the queue (`GET /appeals`):** content id, creator id, submitted and
  appealed timestamps, the original label and attribution, `ai_score`, `confidence`, both signal
  scores with the LLM's indicators and stylometry metrics, the gate note, the first 500
  characters of the text, and the creator's reasoning. Seeing the per-signal scores lets the
  reviewer spot "stylometry alone drove this", which is the most common false-positive pattern.
- **Rate limit:** 5 appeals per hour per IP, so the queue can't be flooded.

## 8. Anticipated edge cases

1. **A poem with heavy repetition and simple vocabulary**, e.g. a refrain repeated every stanza
   with no end punctuation. Line breaks become "sentences" of near-identical length, so
   burstiness goes low (AI-like), while short simple words pull word length down (human-like).
   The result is noisy. The LLM may also read repetitive simple verse as "generic". Expected
   outcome: `uncertain`, possibly an unfair lean toward AI. Mitigation: the dual-signal gate
   prevents a `likely_ai` label unless the LLM independently agrees, and the creator can appeal.
2. **Formal human writing**, such as an academic abstract or the work of a non-native English
   writer trained in a formal register. Stylometry scores it AI-like (long words, no informal
   markers, possible stock phrases like "furthermore"), and the LLM may agree. This is the most
   likely false positive. Mitigation: the asymmetric 0.80 threshold, the requirement that both
   signals clear their own bars, and the appeal path.
3. **AI text prompted to sound casual** ("write like a teenager, lowercase, with typos").
   Stylometry is fooled by design. Only the LLM signal can catch it, and the combination will
   usually land in `uncertain` (false negative). This is accepted given priority #1.
4. **Very short submissions** (a 2-line poem, a 15-word caption). There isn't enough signal.
   Under 20 characters → rejected with `400`; under 25 words → can't be labeled human; under 40
   words → can't be labeled AI. Both cases fall to `uncertain`.
5. **Lightly edited AI output.** A human adds "I've been thinking..." and an em-dash to an AI
   draft. Signals partly disagree, and the expected result is `uncertain`. That's arguably the
   *correct* answer for mixed authorship.

## 9. Rate limiting

- `POST /submit`: **10 per minute and 100 per day per client IP.**
  - A writer submits their own work a few times a day. Even a poet uploading a backlog of a
    chapbook rarely needs more than 10 submissions in a minute.
  - 10/minute stops a script from hammering the endpoint, and every submission costs one Groq
    call, so the limit also protects the free-tier Groq quota shared by all users.
  - 100/day per IP allows a heavy legitimate day (or a small workshop sharing one network)
    while capping a bulk-scraping or flooding attack.
- `POST /appeal`: **5 per hour per IP.** Appeals are rare and go to human reviewers, whose time
  is the scarcest resource.
- Storage: Flask-Limiter with `storage_uri="memory://"` (fine for one process; production
  would use Redis so limits hold across workers).
- `429` responses return JSON: `{"error": "rate_limited", "detail": "10 per 1 minute"}`.

## 10. Audit log

Append-only JSONL at `logs/audit_log.jsonl` (one JSON object per line, written with
`json.dumps` + `"\n"`). Two event types:

- `submission`: `event, timestamp (UTC ISO 8601, Z), content_id, creator_id, attribution,
  confidence, ai_score, llm_score, llm_status, stylometric_score, signals_used, gate_note,
  label_variant, status ("classified"), appeal_filed (false), text_preview (first 200 chars),
  word_count, model`
- `appeal`: `event, timestamp, appeal_id, content_id, creator_id, status ("under_review"),
  appeal_filed (true), appeal_reasoning, original_attribution, original_confidence,
  original_ai_score, llm_score, stylometric_score, original_timestamp`

Content state (current status) lives in SQLite `data/provenance.db`, because status changes
need an update and the log must never be rewritten. The log records history; SQLite records
current state.

## Architecture

```
SUBMISSION FLOW
                                                                    
 client ──POST /submit {text, creator_id}──▶ [Rate limiter 10/min,100/day per IP] ──429──▶ client
                                                   │ request
                                                   ▼
                                         [Input validation] ──400──▶ client
                                                   │ raw text
                         ┌─────────────────────────┴─────────────────────────┐
                         ▼ raw text                                           ▼ raw text
              [Signal 1: LLM judge (Groq)]                      [Signal 2: Stylometry (pure Python)]
                         │ llm_score 0–1 (or null)                            │ stylometric_score 0–1 + metrics
                         └─────────────────────────┬─────────────────────────┘
                                                   ▼
                       [Confidence scorer: 0.6/0.4 blend, disagreement + length shrink, gates]
                                                   │ ai_score, confidence, gate_note
                                                   ▼
                              [Labeler: thresholds 0.80 / 0.35 → 1 of 3 label texts]
                                                   │ attribution, label text
                                     ┌─────────────┼──────────────────────┐
                                     ▼             ▼                      ▼
                          [Content store]   [Audit log JSONL]     response JSON ──200──▶ client
                          (SQLite, status   ("submission" entry,  {content_id, attribution,
                           = classified)     both signal scores)   confidence, label, signals}

APPEAL FLOW

 client ──POST /appeal {content_id, creator_reasoning}──▶ [Rate limiter 5/hour per IP] ──429──▶ client
                                                   │
                                                   ▼
                       [Appeal handler: validate, look up content_id] ──404 / 403 / 409──▶ client
                                                   │ original decision + reasoning
                                     ┌─────────────┴──────────────┐
                                     ▼                            ▼
                     [Content store: status →          [Audit log: "appeal" entry =
                      under_review, save reasoning]     original decision + appeal_reasoning]
                                     │                            │
                                     └─────────────┬──────────────┘
                                                   ▼
                       response {appeal_id, status: under_review, ...} ──200──▶ client

 reviewer ──GET /appeals──▶ [Content store: under_review items + scores + reasoning]
 anyone   ──GET /log────▶  [Audit log: most recent entries]
```

**Narrative:** A submission passes the rate limiter and validation, then the same raw text goes
to two independent signals: an LLM judge that scores semantic "AI-ness" and a stylometric
analyzer that scores structural uniformity. The scorer blends them, pulls the score toward 0.5
when they disagree or the text is short, and enforces the asymmetric gates. The labeler turns
the score into one of three fixed labels, and the decision is saved, logged, and returned. An
appeal looks up that saved decision, flips its status to `under_review`, and logs the
creator's reasoning next to the original scores so a human reviewer has the full picture.
